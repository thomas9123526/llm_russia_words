>
> **이 장에서 배울 내용:** 모델에 내장된 지식만으로는 왜 부족한지 · RAG 파이프라인이 문서를 어떻게 인덱싱하고 검색하고 활용하는지 · RAG가 어디서 실패하며 그것을 어떻게 측정하는지

## 모델이 모르는 것

언어 모델에게 "우리 연구실 내부 안전 규정 4.2절에는 무엇이 쓰여 있나요?"라고 물어봅시다. 모델은 그 문서를 본 적이 없으니 알 수가 없습니다. 운이 좋으면 모른다고 말합니다. 하지만 그럴듯하게 지어낸 답을 내놓는 경우가 더 많습니다. 학습 데이터가 끝나는 시점인 **지식 컷오프(knowledge cutoff)** 이후의 사건이나, 학습 말뭉치에 몇 번밖에 나오지 않은 드문 사실에 대해서도 마찬가지입니다.

모델이 사전 학습에서 배운 모든 것은 가중치에 저장됩니다. 이것을 **파라메트릭 지식(parametric knowledge)** 이라고 부릅니다. 여기에는 세 가지 약점이 있습니다. 학습 시점에 고정되어 있고, 갱신하기 어려우며(새로운 사실로 미세 조정하는 것은 비싸고 믿을 수 없습니다, 제31장), 출처를 알려 주지 않아 답이 어디서 왔는지 확인할 수 없습니다.

**검색 증강 생성(retrieval-augmented generation, RAG)** 은 두 번째 기억, 즉 **비파라메트릭(non-parametric)** 기억을 더합니다. 질문할 때 검색할 수 있는 외부 문서 컬렉션입니다. Lewis et al.(2020)의 논문에서 이름 붙여진 이 아이디어는 간단합니다. 모델이 답하기 전에 질문과 가장 관련 있는 구절을 찾아 프롬프트에 넣는 것입니다. 그러면 모델은 기억해 내는 대신 읽어서 답합니다. 책을 덮고 보는 시험과 책을 펴고 보는 시험의 차이입니다.

이렇게 하면 여러 장점을 한꺼번에 얻습니다. 지식 베이스는 학습 없이 문서를 추가하는 것만으로 갱신됩니다. 비공개 데이터는 자신의 인덱스 안에 머뭅니다. 그리고 답이 출처를 인용할 수 있어 검증이 가능해집니다. RAG는 LLM을 실제로 활용할 때 가장 널리 쓰이는 패턴 중 하나입니다.

## 파이프라인: 인덱싱, 검색, 생성

RAG 시스템은 두 단계로 이루어집니다. 첫 번째 단계는 문서 컬렉션마다 한 번, 오프라인으로 수행합니다.

1. **청킹(chunking).** 각 문서를 수백 토큰 크기의 **청크(chunk)** 로 나눕니다. 청크는 구체적일 만큼, 그리고 여러 개가 문맥 창에 들어갈 만큼 작아야 하지만, 의미를 유지할 만큼은 커야 합니다. 경계에서 잘린 문장이 사라지지 않도록 약간씩 겹치게 나누는 경우가 많습니다.
2. **임베딩.** 임베딩 모델(제22장의 모델들과 비슷한 인코더로, 의미가 비슷한 텍스트가 가까운 벡터를 갖도록 학습된 모델)로 각 청크를 벡터로 바꿉니다.
3. **인덱싱.** 벡터를 **인덱스(index)** 에 저장합니다. 흔히 **벡터 데이터베이스(vector database)** 라고 부릅니다.

두 번째 단계는 질문마다 온라인으로 수행합니다.

4. **검색.** 같은 모델로 질문을 임베딩하고 유사도가 가장 높은 청크 $k$개를 찾습니다.
5. **생성.** 검색된 청크와 질문으로 프롬프트를 만들고 LLM이 답하게 합니다.

유사도로는 보통 제5장에서 만난 **코사인 유사도(cosine similarity)** 를 씁니다.

$$
\cos(\mathbf{q}, \mathbf{d}) = \frac{\mathbf{q} \cdot \mathbf{d}}{\lVert \mathbf{q} \rVert \, \lVert \mathbf{d} \rVert}
$$

여기서 $\mathbf{q}$는 질문 벡터, $\mathbf{d}$는 청크 벡터입니다. 모든 벡터를 길이 1로 정규화해 두면 코사인은 그냥 내적이 되므로, 전체 컬렉션에 대한 검색은 행렬–벡터 곱셈 한 번으로 귀결됩니다.

아래 코드는 완전한 장난감 파이프라인을 만듭니다. 외부 의존성이 없도록 "임베딩"으로 신경망 인코더 대신 정규화된 단어 주머니(bag-of-words) 벡터(제4장)를 썼지만, 나머지 단계는 실제 시스템과 같은 모양입니다.

```python
import numpy as np

docs = [
    "Moscow is the capital of Russia.",
    "Seoul is the capital of South Korea.",
    "The transformer uses self-attention.",
    "LoRA adds low-rank matrices to frozen weights.",
]

def tokens(text):
    return text.lower().replace(".", "").replace("?", "").split()

vocab = sorted({w for d in docs for w in tokens(d)})
def embed(text):                        # 장난감 임베딩: 단어 주머니 벡터
    v = np.array([tokens(text).count(w) for w in vocab], dtype=float)
    return v / (np.linalg.norm(v) + 1e-9)  # 길이 1이므로 내적 = 코사인

index = np.stack([embed(d) for d in docs])   # "벡터 데이터베이스"

def retrieve(question, k=2):
    scores = index @ embed(question)          # 모든 청크와의 코사인 유사도
    top = np.argsort(-scores)[:k]
    return [(docs[i], round(float(scores[i]), 3)) for i in top]

question = "What is the capital of South Korea?"
hits = retrieve(question)
print(hits)
context = "\n".join(f"[{i+1}] {d}" for i, (d, _) in enumerate(hits))
prompt = f"Answer using only the sources.\n{context}\nQuestion: {question}\nAnswer:"
print(prompt)
```

질문에는 어휘 사전에 있는 단어가 여섯 개 있습니다("what"은 없습니다). 서울 문장은 여섯 개를 모두 공유하므로 코사인은 $6 / (\sqrt{6}\,\sqrt{7}) \approx 0.926$입니다. 모스크바 문장은 네 개("is the capital of")를 공유하므로 $4 / (\sqrt{6}\,\sqrt{6}) \approx 0.667$입니다. 최종 프롬프트에서는 출처에 번호를 매겼으므로 모델이 [1], [2]처럼 인용할 수 있습니다.

실제 신경망 인코더라면 "What is the main city of Korea?"라는 질문도 공통 단어가 적은데도 서울 청크를 찾아낼 것입니다. 이것이 DPR(Karpukhin et al., 2020)이 대규모로 도입한 **밀집 검색(dense retrieval)** 의 강점입니다. 두 개의 인코더가 질문과 구절을 하나의 벡터 공간으로 보내며, 질문이 그 질문에 답하는 구절 근처에 놓이도록 학습됩니다.

## 검색을 좋게 만들기

RAG 시스템에서 생성기는 **검색기(retriever)** 가 준 자료만큼만 좋을 수 있습니다. 여러 기법이 검색을 개선합니다.

**희소 검색과 밀집 검색.** 고전적인 **희소 검색(sparse retrieval)** 은 단어의 희귀도로 가중한 단어 겹침을 사용합니다. 표준 공식은 **BM25** 입니다.

$$
\text{BM25}(D, Q) = \sum_{w \in Q} \text{IDF}(w) \cdot \frac{f(w, D)\,(k_1 + 1)}{f(w, D) + k_1\left(1 - b + b\,\frac{|D|}{\text{avgdl}}\right)}
$$

여기서 $f(w, D)$는 단어 $w$가 문서 $D$에 나오는 횟수, $|D|$는 문서 길이, avgdl은 평균 문서 길이, IDF는 제4장의 역문서 빈도이며, $k_1$(보통 1.2–2 정도)과 $b$(보통 0.75)는 포화와 길이 정규화를 조절하는 상수입니다. BM25는 밀집 임베딩이 흐릿해지기 쉬운 정확한 이름, 숫자, 드문 용어에 매우 강합니다. 밀집 검색은 바꿔 말하기(paraphrase)에 더 강합니다. **하이브리드 검색(hybrid search)** 은 두 점수를 결합하며, 종종 어느 한쪽만 쓰는 것보다 낫습니다.

**근사 검색.** 청크가 수백만 개라면 질문을 모든 벡터와 비교하는 것은 너무 느립니다. HNSW(이웃들로 이루어진 계층형 그래프)나 역파일(inverted file)과 곱 양자화(product quantization)에 기반한 라이브러리 같은 **근사 최근접 이웃 탐색(approximate nearest neighbor search, ANN)** 방법은 진짜 이웃을 가끔 놓치는 대가로 거의 같은 top-$k$를 훨씬 빠르게 찾습니다.

**재순위화.** 1단계 검색기는 **바이 인코더(bi-encoder)** 입니다. 질문과 청크를 따로 임베딩하는데, 청크 벡터를 미리 계산해 둘 수 있으므로 빠릅니다. 하지만 두 텍스트는 서로를 "보지" 못합니다. **크로스 인코더(cross-encoder)** 는 질문과 청크를 하나의 트랜스포머로 함께 읽고 관련도 점수를 냅니다. 훨씬 더 정확하지만 전체 컬렉션에 쓰기에는 너무 느립니다. 그래서 먼저 후보를 예컨대 50개 빠르게 검색한 다음, 크로스 인코더로 **재순위화(reranking)** 하여 상위 5개를 남깁니다.

**질의 변환.** 사용자의 질문은 짧거나 모호한 경우가 많습니다. LLM 자신이 질문을 고쳐 쓰거나, 복잡한 질문을 하위 질문으로 나누거나, 가상의 답을 생성해 그 임베딩으로 검색할 수 있습니다(HyDE 방법). 이는 언제 무엇을 검색할지 스스로 정하는 제38장의 에이전트와 자연스럽게 이어집니다.

## RAG는 어디서 실패하며 어떻게 측정하는가

RAG는 환각(제39장)을 줄이지만 없애지는 못합니다. 오류의 원인은 두 가지이며, 이 둘을 구별하는 것이 중요합니다.

- **검색 실패.** 올바른 청크가 top-$k$ 안에 없습니다. 질문이 다른 단어를 쓰거나, 답이 두 청크에 걸쳐 나뉘었거나, 인덱스가 오래되었기 때문입니다. 없는 사실은 어떤 생성기도 고칠 수 없습니다.
- **생성 실패.** 올바른 청크가 프롬프트에 있는데도 모델이 그것을 무시하거나, 파라메트릭 지식과 섞거나, 잘못 읽습니다. Liu et al.(2023)은 **"중간 정보 손실(lost in the middle)"** 효과를 보였습니다. 모델은 긴 문맥의 처음과 끝에 있는 정보를 가운데 있는 정보보다 잘 활용합니다. 순서가 중요하므로 가장 좋은 청크를 앞에 두는 경우가 많습니다.

RAG에만 있는 문제가 두 가지 더 있습니다. 검색된 출처들이 서로 모순되거나 모델 자신의 지식과 모순되면 모델은 누구를 믿을지 정해야 하는데, 그 선택이 늘 우리가 원하는 것은 아닙니다. 또한 검색된 텍스트는 신뢰할 수 없는 입력입니다. 웹 페이지나 문서에 "이전 지시를 무시하고 ..." 같은 지시가 들어 있을 수 있습니다. 이것은 검색을 통한 **프롬프트 인젝션(prompt injection)** 이며, 이런 텍스트를 컬렉션에 심는 공격자는 **검색 오염(retrieval poisoning)** 을 저지르는 것입니다. 이 문제는 제38장과 제40장에서 다시 다룹니다.

RAG 시스템을 평가할 때는 두 단계를 따로 측정합니다.

- 검색에는 **recall@k(재현율@k)** 를 씁니다. 관련 청크가 적어도 하나 top-$k$ 안에 들어간 질문의 비율입니다. 이를 위해서는 관련 청크가 표시된 질문 집합이 필요합니다.
- 생성에는 **충실성(faithfulness)** 과 **답의 정확성(answer correctness)** 을 씁니다. 충실성은 답의 모든 주장이 검색된 텍스트로 뒷받침되는지, 정확성은 답이 정답과 일치하는지를 봅니다. 답은 틀린 출처에 충실할 수도 있고, 근거 없이 우연히 맞을 수도 있습니다. 우리는 둘 다를 원합니다.

실제로는 각 주장을 출처와 대조하는 다른 LLM이 충실성을 판정하는 경우가 많은데, 이 방법에는 제39장에서 다룰 고유한 편향이 있습니다. 자기 분야에서 직접 손으로 라벨을 단 작은 테스트 세트를 항상 갖고 있는 것이 좋은 습관입니다. 일반 벤치마크는 여러분의 문서에 대해 알려 주는 것이 거의 없기 때문입니다.

RAG만이 모델에 새 지식을 주는 방법은 아닙니다. 긴 문맥 모델은 때로 문서 전체를 직접 읽을 수 있고, 미세 조정은 문체와 분야의 형식을 가르칠 수 있습니다. 실제로는 이들이 잘 어울립니다. 미세 조정은 출처를 *어떻게* 쓰는지 가르치고, 검색은 *어떤* 출처를 쓸지 제공합니다.

## 요약

- 가중치 속의 파라메트릭 지식은 고정되어 있고 갱신하기 어려우며 출처를 알려 주지 않습니다. RAG는 검색 가능한 비파라메트릭 기억을 더합니다.
- 파이프라인: 문서를 청크로 나누고 임베딩해 인덱싱합니다. 질문이 오면 질문을 임베딩하고 top-$k$ 청크를 검색해 그것으로 답을 생성합니다.
- 밀집 검색은 바꿔 말하기에, 희소 검색 BM25는 정확한 용어에 강합니다. 하이브리드 검색, 근사 최근접 이웃 인덱스, 크로스 인코더 재순위화가 품질과 속도를 높입니다.
- 실패는 검색(올바른 청크가 없음) 또는 생성(모델이 무시하거나 잘못 읽음, 예: 중간 정보 손실)에서 옵니다.
- 검색은 recall@k로, 생성은 충실성과 정확성으로 평가합니다. 검색된 텍스트는 신뢰할 수 없는 입력으로 다룹니다.

## 연습 문제

1. 파라메트릭 지식과 비파라메트릭 지식의 차이를 자신의 말로 설명하고, 각각이 더 나은 과제를 하나씩 예로 드세요.
2. 코드의 질문과 "The transformer uses self-attention." 사이의 코사인 유사도를 손으로 계산하세요. 그런 다음 `retrieve(question, k=4)`를 실행해 답을 확인하세요.
3. `retrieve("Which city is the Korean capital?")`를 실행해 보세요. 어떤 문서가 1위가 되며, 왜 여기서 단어 주머니 매칭이 실패합니까("Korean"과 "Korea"라는 단어를 보세요)? 밀집 인코더라면 무엇이 달라질까요?
4. recall@5가 0.95인데도 사용자들은 절반의 경우 답이 틀린다고 보고합니다. 어디부터 살펴보겠습니까? 어떤 지표를 추가하겠습니까?
