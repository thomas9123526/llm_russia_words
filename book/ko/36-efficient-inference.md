## 텍스트 생성은 왜 이렇게 느릴까?

70억 개 파라미터를 가진 모델을 학습시킨 뒤 500토큰짜리 답변을 써 달라고 요청한다고 합시다. 학습할 때는 여러 GPU에서 초당 수백만 토큰을 처리했는데, 답변은 한 토큰씩, 아마 초당 수십 토큰 정도의 속도로 나타납니다. 왜 그럴까요?

제24장에서 보았듯이 생성은 **자기회귀적(autoregressive)** 입니다. 토큰 $t+1$을 만들려면 모델에 토큰 $1, \dots, t$가 필요합니다. 토큰 499가 생기기 전에 토큰 500을 계산할 수는 없습니다. 학습 중에는 전체 텍스트를 미리 알고 있으므로 시퀀스의 모든 위치를 병렬로 처리합니다(제21장). 생성 중에는 시퀀스가 한 단계씩 자라므로, 새 토큰마다 네트워크 전체를 한 번씩 실행해야 합니다.

**추론(inference)** 은 두 단계로 나누어 보면 이해하기 쉽습니다.

- **프리필(prefill).** 프롬프트는 전부 알려져 있으므로 모든 토큰을 한 번의 병렬 순전파로 처리합니다. 이 단계는 주로 산술 연산에 의해 제한됩니다. 커다란 행렬–행렬 곱셈이 GPU를 바쁘게 만듭니다. 이 단계가 **첫 토큰까지의 시간(time to first token)** 을 결정합니다.
- **디코딩.** 새 토큰마다 한 위치만 처리하는 순전파가 한 번 필요합니다. 이제 모든 가중치 행렬이 벡터 하나와 곱해집니다. GPU는 아주 적은 연산을 하기 위해 모든 가중치를 메모리에서 읽어 와야 합니다.

두 번째 항목이 이 장의 핵심입니다. 16비트 정밀도의 7B 모델은 가중치가 약 14GB입니다. 토큰 하나를 생성하려면 GPU는 14GB 전체를 메모리에서 읽어야 합니다. **메모리 대역폭(memory bandwidth)** 이 예컨대 1TB/s라면 이것만으로 약 14ms가 걸리고, 연산 장치가 아무리 빨라도 초당 약 70토큰으로 제한됩니다. 이런 상황을 디코딩이 연산 제약(compute-bound)이 아니라 **메모리 제약(memory-bound)** 이라고 말합니다.

여기서 세 가지 전략이 나오며, 아래의 각 절에서 하나씩 다룹니다.

1. 이미 계산한 것은 다시 계산하지 않는다(KV 캐시).
2. 가중치를 작게 만들어 읽을 양을 줄인다(양자화).
3. 가중치를 한 번 비싸게 읽을 때마다 토큰을 두 개 이상 얻는다(추측 디코딩, 배칭).

## KV 캐시

제15장의 셀프 어텐션을 떠올려 봅시다. 단계 $t$에서 새 토큰의 쿼리 $q_t$는 지금까지 모든 토큰의 키 $k_1, \dots, k_t$와 비교되고, 결과는 그 값 $v_1, \dots, v_t$의 가중합입니다.

$$
o_t = \sum_{i=1}^{t} \operatorname{softmax}_i\!\left(\frac{q_t \cdot k_i}{\sqrt{d}}\right) v_i
$$

여기서 $d$는 헤드 차원입니다. 인과적 마스크가 있는 디코더(제16장)에서 토큰 $i$의 키와 값은 토큰 $1, \dots, i$에만 의존합니다. 이후 토큰이 들어와도 절대 바뀌지 않습니다. 따라서 매 단계마다 $k_1, \dots, k_{t-1}$과 $v_1, \dots, v_{t-1}$을 다시 계산하는 것은 낭비입니다. 한 번 계산해서 저장해 두고, 단계 $t$에서는 새 토큰의 $q_t, k_t, v_t$만 계산합니다. 이 저장소를 **KV 캐시(KV cache)** 라고 합니다.

아래 코드는 어텐션 헤드 하나에서 캐시를 사용한 계산이 전체 재계산과 정확히 같은 출력을 낸다는 것을 확인합니다.

```python
import torch

torch.manual_seed(0)
d, T = 8, 5                       # 임베딩 크기, 토큰 수
x = torch.randn(T, d)             # 토큰 5개의 은닉 상태
Wq, Wk, Wv = (torch.randn(d, d) for _ in range(3))

def attend(q, K, V):
    w = torch.softmax(q @ K.T / d**0.5, dim=-1)
    return w @ V

# 캐시 없음: 매 단계마다 접두부 전체의 K와 V를 다시 계산
full = [attend(x[t] @ Wq, x[:t+1] @ Wk, x[:t+1] @ Wv) for t in range(T)]

# KV 캐시 사용: 새 토큰의 K와 V만 계산해서 덧붙임
K_cache, V_cache, cached = [], [], []
for t in range(T):
    K_cache.append(x[t] @ Wk)
    V_cache.append(x[t] @ Wv)
    K, V = torch.stack(K_cache), torch.stack(V_cache)
    cached.append(attend(x[t] @ Wq, K, V))

print(torch.allclose(torch.stack(full), torch.stack(cached), atol=1e-6))  # True
```

캐시는 새 토큰마다 키와 값을 만드는 비용을 $O(t)$에서 $O(1)$로 바꿉니다. 하지만 공짜는 아닙니다. 메모리를 소비합니다. 모든 층, 모든 키–값 헤드, 모든 토큰마다 벡터 두 개(키와 값)를 저장합니다. 크기는 다음과 같습니다.

$$
\text{KV 메모리} = 2 \cdot L \cdot H_{kv} \cdot d_{head} \cdot T \cdot b
$$

여기서 $L$은 층 수, $H_{kv}$는 키–값 헤드 수, $d_{head}$는 헤드 차원, $T$는 토큰 수, $b$는 숫자 하나당 바이트 수입니다. $L = 32$, $H_{kv} = 8$, $d_{head} = 128$, 16비트 숫자($b = 2$), 문맥 길이 $T = 4096$인 모델을 생각해 봅시다.

$$
2 \cdot 32 \cdot 8 \cdot 128 \cdot 4096 \cdot 2 = 536{,}870{,}912 \text{ 바이트} = 512 \text{ MiB}
$$

시퀀스 하나에 대해 토큰당 128KiB입니다. 사용자 32명이 동시에 쓰면 캐시에 16GiB가 필요한데, 이는 양자화된 7B 모델의 가중치보다 큽니다. 이제 그룹 쿼리 어텐션(grouped-query attention, 제25장)이 왜 중요한지 알 수 있습니다. 키–값 헤드가 8개가 아니라 32개라면 캐시는 네 배가 됩니다. 긴 문맥을 서비스할 때는 가중치보다 KV 캐시 메모리가 병목이 되는 경우가 많습니다.

서빙 시스템은 이 메모리를 신중하게 관리합니다. vLLM 시스템에서 제안된 **PagedAttention** 은 캐시를 운영체제의 페이지처럼 작은 고정 크기 블록에 저장하여, 예약만 되고 쓰이지 않는 공간에 메모리가 낭비되지 않게 합니다. **연속 배칭(continuous batching)** 은 다른 요청이 끝나는 즉시 새 요청을 실행 중인 배치에 추가합니다. 배칭이 도움이 되는 이유는 바로 디코딩이 메모리 제약이기 때문입니다. 가중치를 한 번 읽어 여러 시퀀스를 동시에 처리할 수 있으므로, 각 요청의 **지연 시간(latency)** 은 그대로이거나 약간 늘어나더라도 전체 **처리량(throughput)** 은 거의 공짜로 늘어납니다.

## 양자화

두 번째 전략은 숫자를 더 적은 비트로 저장하는 것입니다. **양자화(quantization)** 는 스케일 인자 $s$를 사용해 부동소수점 가중치 $w$를 작은 정수 $q$로 대응시킵니다.

$$
q = \operatorname{round}\!\left(\frac{w}{s}\right), \qquad \hat{w} = s \cdot q, \qquad s = \frac{\max |w|}{127}
$$

이것은 8비트 정수(INT8)로의 **absmax** 양자화입니다. 절댓값이 가장 큰 값이 127에 대응되고, $\hat{w}$는 복원된(역양자화된) 가중치입니다. 차이 $w - \hat{w}$가 반올림 오차입니다. INT8은 16비트에 비해 메모리를 절반으로, INT4는 4분의 1로 줄이므로 7B 모델이 약 3.5GB에 들어갑니다.

```python
import numpy as np

rng = np.random.default_rng(0)
W = rng.normal(0, 0.02, size=(256, 256)).astype(np.float32)  # 가중치 행렬

def quantize_int8(w):
    scale = np.abs(w).max() / 127          # absmax: 가장 큰 값을 127에 대응
    q = np.round(w / scale).astype(np.int8)
    return q, scale

def dequantize(q, scale):
    return q.astype(np.float32) * scale

q, s = quantize_int8(W)
W_hat = dequantize(q, s)
print("bytes fp32:", W.nbytes, " bytes int8:", q.nbytes)   # 262144 대 65536
print("mean abs error:", np.abs(W - W_hat).mean())

W[0, 0] = 1.0                                # 보통 값보다 50배 큰 이상치 하나
q, s = quantize_int8(W)
print("error with outlier:", np.abs(W - dequantize(q, s)).mean())
```

마지막 세 줄이 핵심적인 어려움을 보여 줍니다. **이상치(outlier)** 하나가 행렬 전체의 스케일을 정하므로, 평범한 작은 가중치들이 몇 개 안 되는 정수 수준으로 뭉개지고 평균 오차가 약 열 배 커집니다. 실제 LLM에는 특히 활성값에 이런 이상치가 실제로 있습니다. 실용적인 방법들은 여러 방식으로 이에 대응합니다.

- **더 세밀한 단위.** 행, 열, 또는 64개나 128개 가중치로 이루어진 작은 그룹마다 별도의 스케일을 써서, 이상치가 자기 그룹에만 영향을 주게 합니다.
- **이상치를 높은 정밀도로 유지.** LLM.int8()은 소수의 이상치 특성 차원은 16비트로, 나머지는 8비트로 처리합니다.
- **오차를 고려한 반올림.** GPTQ는 작은 보정(calibration) 데이터셋을 이용해 가중치를 한 열씩 양자화하면서 남은 가중치를 조정해 오차를 보상합니다. AWQ는 어떤 가중치가 큰 활성값과 만나는지 관찰하고 재스케일링으로 그 가중치를 보호합니다.

이들은 **학습 후 양자화(post-training quantization)** 방법입니다. 모델을 높은 정밀도로 학습한 뒤 재학습 없이 압축합니다. 제32장에서 본 QLoRA는 4비트 기반 모델을 고정한 채 그 위에서 LoRA 어댑터를 학습합니다. 양자화는 메모리 사용량을 줄이고, 디코딩이 메모리 제약이므로 토큰당 시간도 줄입니다. 그 대가는 어느 정도의 품질 손실인데, 8비트에서는 보통 작고 3비트 이하에서는 눈에 띕니다. KV 캐시도 양자화할 수 있습니다.

## 추측 디코딩

세 번째 전략은 순차성이라는 병목 자체를 공략합니다. 아이디어는 이렇습니다. 작고 빠른 **초안 모델(draft model)** 이 다음 $k$개 토큰을 추측하고, 큰 **목표 모델(target model)** 이 한 번의 순전파로 $k$개 추측을 모두 검사합니다. 디코딩은 메모리 제약이라 어느 쪽이든 가중치를 한 번 읽으므로, $k$개 토큰을 병렬로 검사하는 비용은 하나를 생성하는 비용과 거의 같습니다.

어떻게 검사할까요? $q(x)$를 초안 모델이 토큰 $x$에 부여한 확률, $p(x)$를 목표 모델의 확률이라고 합시다. 제안된 각 토큰에 대해 왼쪽에서 오른쪽으로 다음을 수행합니다.

1. 확률 $\min\!\left(1, \dfrac{p(x)}{q(x)}\right)$로 토큰을 수락합니다.
2. 거부되면 보정된 분포 $\propto \max(0, p(x) - q(x))$에서 대체 토큰을 샘플링하고, 이후의 초안 토큰은 모두 버립니다.
3. $k$개가 모두 수락되면 목표 모델의 순전파에서 토큰 하나를 덤으로 얻습니다.

**기각 샘플링(rejection sampling)** 의 일종인 이 규칙에는 원 논문들(Leviathan et al.; Chen et al., 둘 다 2023년)에서 증명된 놀라운 성질이 있습니다. 수락된 토큰은 목표 모델 혼자 샘플링한 것과 **정확히** 같은 분포를 따릅니다. **추측 디코딩(speculative decoding)** 은 근사가 아니며, 바뀌는 것은 속도뿐입니다.

얼마나 빨라질까요? 각 초안 토큰이 확률 $\alpha$(**수락률**, acceptance rate)로 수락된다면, 목표 모델 순전파 한 번당 생성되는 토큰 수의 기댓값은 다음과 같습니다.

$$
\frac{1 - \alpha^{k+1}}{1 - \alpha}
$$

$\alpha = 0.8$, $k = 4$이면 $(1 - 0.8^5)/(1 - 0.8) = (1 - 0.32768)/0.2 \approx 3.36$으로, 순전파 한 번에 1개가 아니라 약 3.36개의 토큰을 얻습니다. 초안 모델도 시간이 들기 때문에 실제 속도 향상은 이보다 작지만, 두세 배 정도는 흔합니다. 수락률은 예측하기 쉬운 텍스트(코드, 반복 문구)에서 높고 창의적인 텍스트에서 낮습니다. 별도의 초안 모델 없이 하는 변형도 있습니다. Medusa는 목표 모델에 추가 예측 헤드를 붙이고, 어떤 방법들은 프롬프트에서 찾은 n-그램으로 초안을 만듭니다.

다른 기법들이 그림을 완성합니다. **FlashAttention** 은 칩 위의 빠른 메모리에 머무는 타일 단위로 어텐션을 계산하여 메모리 이동을 줄입니다. **지식 증류(knowledge distillation)** 는 작은 모델이 큰 모델을 모방하도록 학습시킵니다. **가지치기(pruning)** 는 중요하지 않은 가중치를 제거합니다. 전문가 혼합 모델(제29장)은 토큰마다 가중치의 일부만 읽습니다. 이 모든 방법의 목표는 하나입니다. 이동하는 바이트는 줄이고, 연산은 줄이고, 초당 유용한 토큰은 늘리는 것입니다.

## 요약

- 생성은 자기회귀적입니다. 프리필은 프롬프트를 병렬로 처리하고, 디코딩은 순전파 한 번에 토큰 하나를 만들며 보통 메모리 제약입니다.
- KV 캐시는 과거 토큰의 키와 값을 저장해 다시 계산하지 않게 합니다. 그 메모리는 층 수, KV 헤드 수, 헤드 크기, 문맥 길이에 비례해 늘어납니다.
- 페이지 단위 메모리 관리와 연속 배칭 덕분에 서버는 가중치를 한 번 읽어 여러 요청을 처리할 수 있고, 처리량이 높아집니다.
- 양자화는 가중치(때로는 활성값이나 KV 캐시)를 8비트나 4비트로 저장합니다. 주된 오차 원인은 이상치이며, 그룹별 스케일과 GPTQ, AWQ 같은 오차 인식 방법으로 다룹니다.
- 추측 디코딩에서는 초안 모델이 토큰을 제안하고 목표 모델이 한 번의 순전파로 검증합니다. 수락 규칙 덕분에 출력 분포는 정확히 그대로 유지됩니다.

## 연습 문제

1. 시퀀스 하나를 디코딩하는 것은 메모리 제약인데 프리필 단계는 연산 제약인 이유를 자신의 말로 설명해 보세요.
2. $L = 40$, $H_{kv} = 8$, $d_{head} = 128$, 16비트 숫자, 문맥 길이 8192토큰인 모델의 KV 캐시 크기를 계산하세요. 캐시를 INT8로 저장하면 어떻게 달라집니까?
3. 양자화 코드를 `W`의 행마다 별도의 스케일을 쓰도록 고쳐 보세요(힌트: `np.abs(w).max(axis=1, keepdims=True)`). 이상치가 있을 때의 오차를 행렬 전체에 스케일 하나를 쓰는 경우와 비교하세요.
4. $k = 4$일 때 $\alpha = 0.5$와 $\alpha = 0.9$에 대해 목표 모델 순전파당 토큰 수의 기댓값을 계산하세요. 이 결과는 초안 모델 선택에 대해 무엇을 알려 줍니까?
