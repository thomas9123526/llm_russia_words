## 단어의 길이는 얼마인가?

같은 뜻을 가진 세 단어, 영어 *cat*, 러시아어 *кот*, 한국어 *고양이*를 생각해 봅시다. 셋 다 문자가 세 개입니다. 그런데 각 단어를 파일로 저장하면 파일 크기가 다릅니다. 3바이트, 6바이트, 9바이트입니다. 왜 그럴까요?

제1장에서 언어 모델은 토큰의 시퀀스를 다룬다고 했습니다. 텍스트를 토큰으로 나누기 전에, 먼저 컴퓨터 안에서 텍스트가 *무엇인지* 이해해야 합니다. 컴퓨터는 숫자만 저장합니다. 따라서 모든 글자, 숫자, 공백, 이모지는 숫자로 바뀌어야 하고, 그 숫자들은 바이트로 기록되어야 합니다. 이 장에서는 그 과정이 어떻게 이루어지는지, 그리고 그 세부 사항이 언어 모델에, 특히 러시아어와 한국어 같은 언어에 왜 중요한지 설명합니다.

## 문자와 코드 포인트

첫 단계는 모든 **문자**(character)에 번호를 부여하는 것입니다. 이를 위한 국제 표준이 **유니코드**(Unicode)입니다. 유니코드는 각 문자에 **코드 포인트**(code point)라고 부르는 고유한 정수를 부여하며, 이를 접두사 `U+`와 함께 16진수로 씁니다. 예를 들면 다음과 같습니다.

- 라틴 문자 *c*는 U+0063(10진수 99)입니다.
- 키릴 문자 *к*는 U+043A(10진수 1082)입니다.
- 한글 음절 *고*는 U+ACE0(10진수 44256)입니다.

코드 포인트는 U+0000부터 U+10FFFF까지이며, 백만 개가 넘는 문자를 담을 공간이 있습니다. 여기에는 세계의 문자 체계, 수학 기호, 이모지 등이 포함됩니다. 이 수준에서 텍스트는 단순히 코드 포인트의 시퀀스입니다. 파이썬에서 `ord("к")`는 문자의 코드 포인트를 돌려주고, `chr(1082)`는 그 반대로 변환합니다.

한국어는 흥미로운 경우입니다. 현대 한글에는 초성 19개, 중성 21개, 종성 28가지(종성 자음 27개와 "종성 없음")가 있습니다. 유니코드는 가능한 모든 음절을 별도의 문자로 담고 있으며, 그 수는 모두 $19 \cdot 21 \cdot 28 = 11{,}172$개이고 U+AC00에서 시작하는 블록에 있습니다. 음절의 코드 포인트는 간단한 공식으로 계산됩니다.

$$\text{code} = \text{0xAC00} + (21 \cdot i + m) \cdot 28 + f,$$

여기서 $i$는 초성의 번호(0–18), $m$은 중성의 번호(0–20), $f$는 종성의 번호(0–27, 0은 "종성 없음")입니다. *한*의 경우 ㅎ은 $i = 18$, ㅏ는 $m = 0$, ㄴ은 $f = 4$이므로 코드는 $44032 + 378 \cdot 28 + 4 = 54620$, 즉 U+D55C입니다.

## 코드 포인트에서 바이트로: 인코딩

코드 포인트는 추상적인 숫자입니다. 이를 메모리나 파일에 저장하려면 코드 포인트를 **바이트**(byte)의 시퀀스로 바꾸는 규칙, 즉 **문자 인코딩**(character encoding)이 필요합니다. 바이트는 8비트이며 0부터 255까지의 값을 담을 수 있습니다.

가장 오래되고 널리 쓰인 인코딩은 **ASCII**입니다. ASCII는 128개의 문자(영어 알파벳, 숫자, 구두점, 제어 코드)만 정의하며, 각 문자를 1바이트에 저장합니다. ASCII에는 키릴 문자도 한글도 없습니다. 수십 년 동안 나라마다 서로 호환되지 않는 고유한 인코딩을 사용했습니다(예를 들어 러시아어는 KOI8-R과 Windows-1251, 한국어는 EUC-KR). 한 인코딩으로 쓴 파일을 다른 인코딩으로 읽으면 깨진 글자가 되었습니다. 러시아어에는 이렇게 깨진 글자를 가리키는 단어 *кракозябры*까지 있습니다.

오늘날 지배적인 인코딩은 **UTF-8**입니다. UTF-8은 코드 포인트마다 서로 다른 바이트 수를 사용합니다.

| 코드 포인트 범위 | 바이트 수 | 예 |
|---|---|---|
| U+0000 – U+007F | 1 | 영어 알파벳, 숫자(ASCII와 동일) |
| U+0080 – U+07FF | 2 | 키릴 문자, 그리스 문자, 아랍 문자 |
| U+0800 – U+FFFF | 3 | 한글, 한자 |
| U+10000 – U+10FFFF | 4 | 이모지, 드문 문자 체계 |

이제 처음 질문에 답할 수 있습니다. *cat*은 $3 \cdot 1 = 3$바이트, *кот*는 $3 \cdot 2 = 6$바이트, *고양이*는 $3 \cdot 3 = 9$바이트를 차지합니다. UTF-8에는 두 가지 큰 장점이 있습니다. 모든 ASCII 텍스트는 그대로 유효한 UTF-8이며, 여러 바이트로 된 문자의 바이트는 결코 ASCII 문자와 혼동되지 않으므로 프로그램은 언제나 문자가 시작하는 위치를 찾을 수 있습니다.

다음 코드는 세 단어의 코드 포인트와 UTF-8 바이트를 보여 줍니다.

```python
import unicodedata

for word in ["cat", "кот", "고양이"]:
    codes = [f"U+{ord(ch):04X}" for ch in word]   # 유니코드 코드 포인트
    data = word.encode("utf-8")                    # UTF-8 바이트
    print(word, len(word), codes, len(data), list(data))

# 눈에 보이는 문자 하나, 가능한 표현 두 가지
for s in ["ё", "한"]:
    nfd = unicodedata.normalize("NFD", s)          # 분해된 형태
    print(s, len(s), len(nfd), [f"U+{ord(c):04X}" for c in nfd])
    print(nfd == s, unicodedata.normalize("NFC", nfd) == s)
```

첫 번째 반복문은 예를 들어 `кот 3 ['U+043A', 'U+043E', 'U+0442'] 6 [208, 186, 208, 190, 209, 130]`을 출력합니다. 문자 세 개, 바이트 여섯 개입니다. 두 번째 반복문은 다음 절의 주제입니다.

언어 모델이 왜 바이트에 신경 써야 할까요? 일부 현대 토크나이저는 문자가 아니라 256가지 가능한 바이트 값에서 출발합니다(이 "바이트 수준" 접근법은 제3장에서 봅니다). 이런 토크나이저에게 한글 음절 하나는 병합 전에 세 단위이고, 러시아어 글자 하나는 두 단위입니다. 이것이 같은 문장이라도 언어에 따라 토큰 수가 다르게 드는 이유 중 하나입니다.

## 정규화: 하나의 텍스트, 여러 형태

유니코드는 일부 문자를 두 가지 이상의 방식으로 쓰는 것을 허용합니다. 러시아어 글자 *ё*는 코드 포인트 하나(U+0451)일 수도 있고, 글자 *е*(U+0435) 뒤에 결합용 분음 부호(U+0308)가 붙은 두 개일 수도 있습니다. 화면에서는 둘이 똑같아 보입니다. 마찬가지로 한글 음절 *한*은 완성형 코드 포인트 하나(U+D55C)로 저장할 수도 있고, 세 개의 낱자 ㅎ, ㅏ, ㄴ(U+1112, U+1161, U+11AB)으로 저장할 수도 있습니다. 프로그램의 두 번째 반복문이 바로 이것을 보여 줍니다. *ё*의 분해된 형태는 길이가 2, *한*의 분해된 형태는 길이가 3이며, 문자열로서 원래 것과 같지 *않습니다*.

컴퓨터에게는 코드 포인트가 하나만 달라도 두 문자열은 다른 것입니다. 학습 데이터에 두 형태가 모두 있으면, 사람은 하나로 보는 단어를 모델은 "서로 다른" 두 단어로 보게 됩니다. 해결책은 **텍스트 정규화**(text normalization), 즉 이후 처리에 앞서 텍스트를 하나의 표준 형태로 바꾸는 것입니다. 유니코드는 표준 정규화 형식을 정의하며, 그중 가장 흔한 것은 다음과 같습니다.

- **NFC**(조합형): 가능한 경우 문자들을 완성형 코드 포인트로 합칩니다.
- **NFD**(분해형): 문자를 기본 문자와 결합용 부호로 나눕니다.

우리 프로그램은 NFC가 분해된 형태를 원래 형태로 되돌린다는 것을 확인해 줍니다(마지막 열의 `True`). 대부분의 자연어 처리 파이프라인은 NFC나, 전각 라틴 문자 같은 "호환" 문자를 일반 형태로 바꾸는 관련 형식인 **NFKC**를 적용합니다.

정규화는 더 나아갈 수 있으며, 각 단계는 설계상의 선택입니다. **소문자화**(lowercasing)는 *Кот*와 *кот*를 같은 토큰으로 만들지만 정보를 잃기도 합니다(회사 *Apple*과 과일 *apple*). 러시아어 텍스트에서는 *ё* 대신 *е*를 쓰는 경우가 많으므로(*ещё* 대신 *еще*), 어떤 시스템은 모든 *ё*를 *е*로 바꿉니다. 현대의 대규모 언어 모델은 대개 가벼운 정규화만 하고 대소문자, 구두점, 띄어쓰기를 유지합니다. 사람이 쓰는 그대로 텍스트를 생성해야 하기 때문입니다.

## 단어란 무엇인가?

지금까지는 문자를 다루었습니다. 그러나 사람은 단어로 생각하고, 초기 자연어 처리 시스템은 단어를 기본 단위로 다루었습니다. 그렇다면 단어란 정확히 무엇일까요?

영어에서 첫 번째 답은 "공백 사이에 있는 글자들의 시퀀스"입니다. 이것만으로도 문제가 있습니다. *don't*는 한 단어일까요, 두 단어일까요? *New York*은 하나의 단위일까요? *state-of-the-art*는 어떨까요? 텍스트를 단위로 나누는 과정을 **토큰화**(tokenization)라고 하는데, 영어에서조차 그 규칙이 분명하지 않습니다.

다른 언어에서는 문제가 심각해집니다.

- **러시아어**는 풍부한 **형태론**(morphology, 단어가 형태를 바꾸는 방식)을 가지고 있습니다. 명사 하나가 열두 개 정도의 형태를 가집니다. *кот, кота, коту, котом, коте, коты, котов, котам…* 동사는 훨씬 더 많습니다. 각 형태를 별도의 단어로 다루면 어휘 집합이 거대해지고, 각 형태는 데이터에서 더 드물게 나타납니다.
- **한국어**는 교착어입니다. 문법적 조사와 어미가 단어에 붙습니다. *고양이가, 고양이를, 고양이는, 고양이에게*는 모두 *고양이*를 포함하지만, 공백 기준 분리기는 이들을 서로 관계없는 네 단어로 다룹니다. 한국어 띄어쓰기 규칙도 복잡하며, 비격식 글에서는 자주 지켜지지 않습니다.
- **중국어**와 **일본어**는 단어 사이에 공백을 전혀 쓰지 않으므로 "공백으로 나누기"가 통하지 않습니다.

언어학자들은 단어에서 의미를 가진 가장 작은 부분을 **형태소**(morpheme)라고 부릅니다. *котами*에서 어간 *кот-*는 "고양이"라는 의미를, 어미 *-ами*는 "조격 복수"를 나타냅니다. 이상적으로는 모델이 한 단어의 모든 형태가 의미를 공유한다는 것을 알아야 합니다. 이러한 어려움이 제3장의 주제인 **서브워드 토큰화**(subword tokenization)의 주된 동기입니다. 문자(너무 작음)와 단어(너무 많음) 사이에서 고르는 대신, 그 중간에 있는 단위를 학습합니다.

## 기호에서 숫자로

문자, 바이트, 단어, 서브워드 중 무엇을 단위로 고르든 마지막 단계는 같습니다. 모든 단위의 목록인 어휘 집합을 정하고, 각 단위에 정수 **인덱스**, 즉 **토큰 ID**(token ID)를 부여합니다. 예를 들어 어휘 집합이 `["кот", "собака", "чай"]`라면 *кот*는 인덱스 0, *собака*는 인덱스 1, *чай*는 인덱스 2를 받습니다. 텍스트는 정수의 목록이 되고, 모델이 실제로 받는 것은 이 목록입니다.

인덱스는 이름에 불과합니다. 숫자 2가 0보다 의미 있는 뜻에서 "더 큰" 것은 아닙니다. 이런 잘못된 순서 없이 신경망에 입력을 주기 위해 **원-핫 벡터**(one-hot vector)를 사용할 수 있습니다. 이는 길이가 $V$(**어휘 집합 크기**, vocabulary size)인 벡터로, 해당 토큰의 위치에만 1이 있고 나머지는 모두 0입니다. 우리의 작은 어휘 집합에서는 다음과 같습니다.

$$\text{кот} = (1, 0, 0), \quad \text{собака} = (0, 1, 0), \quad \text{чай} = (0, 0, 1).$$

원-핫 벡터는 단순하지만 낭비가 큽니다. 어휘 집합이 50,000개 토큰이면 각 벡터에 0이 49,999개 있습니다. 또한 의미에 대해 아무것도 말해 주지 않습니다. *кот*와 *собака*의 벡터는 *кот*와 *чай*의 벡터와 정확히 같은 정도로 다릅니다. 제5장에서는 이를 임베딩이라고 부르는 짧고 조밀한 벡터로 바꿀 것입니다. 임베딩에서는 비슷한 단어가 비슷한 벡터를 얻습니다.

## 요약

- 유니코드는 모든 문자에 코드 포인트를 부여합니다. 텍스트는 코드 포인트의 시퀀스입니다.
- UTF-8 같은 인코딩은 코드 포인트를 바이트로 바꿉니다. UTF-8에서 영어 글자는 1바이트, 키릴 글자는 2바이트, 한글 음절은 3바이트를 차지합니다.
- 눈에 보이는 같은 텍스트도 서로 다른 코드 포인트 시퀀스를 가질 수 있습니다(예: 완성형과 분해형 *ё*나 *한*). 정규화(NFC, NFKC)는 이들을 동일하게 만듭니다.
- "단어"는 단순한 개념이 아닙니다. 러시아어 형태론, 한국어 조사, 공백 없는 언어 모두 단어 기반 처리를 어렵게 합니다.
- 마지막으로 모든 단위는 정수 인덱스를 받습니다. 원-핫 벡터는 잘못된 순서 없이 인덱스를 표현하지만, 크고 의미를 담지 않습니다.

## 연습 문제

1. 문자, 코드 포인트, 바이트의 차이를 자신의 말로 설명하십시오.
2. 한글 음절 공식을 사용하여 *각*의 코드 포인트를 계산하십시오(ㄱ: $i = 0$; ㅏ: $m = 0$; 종성 ㄱ: $f = 1$). 파이썬에서 `ord("각")`으로 답을 확인하십시오.
3. 문자열 *"Привет, 세계!"*를 UTF-8로 인코딩하면 몇 바이트입니까? 먼저 손으로 계산한 다음 `len(s.encode("utf-8"))`로 확인하십시오.
4. 러시아어 단어 *книга*의 형태 열 개와 한국어 단어 *책*에 조사가 붙은 형태 다섯 개를 적어 보십시오. 단어 수준 어휘 집합은 이들에 대해 어떤 문제를 겪게 됩니까?
